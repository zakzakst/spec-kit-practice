# ドキュメントと ADR

## 概要

コードだけでは意図は残りません。ドキュメントは、使い方、制約、前提、運用方法を伝えます。ADR は、なぜその判断をしたのかを残します。両方とも、将来の手戻りを減らすための投資です。

## 使う場面

- 新しい機能やシステムの使い方を説明したいとき
- 重要なアーキテクチャ判断を残したいとき
- チームで共有したい運用手順があるとき
- 将来の移行や退役に備えたいとき

## 原則

### 1. 何をしたかより、なぜかを書く

読者が知りたいのは、単なる結果ではなく判断理由です。

```text
良い:
- Why: 運用負荷を下げるために managed service を選んだ
- Trade-off: コストは上がるが、保守作業を減らせる

悪い:
- We chose managed service
```

### 2. 1 文書 1 目的

1 つの文書にすべてを詰め込まないでください。使い方、設計、運用、移行は分けます。

### 3. 読む人を先に考える

新規参加者、将来の保守者、オンコール担当、レビューアーが読みやすいように書きます。専門用語は必要なら説明します。

### 4. 更新しやすくする

文書は置きっぱなしではなく、変更に追随できる形で保ちます。古くなった文書は、ない文書より危険です。

## ドキュメントの種類

### User-Facing Docs

- 機能の使い方
- よくあるトラブル
- FAQ
- 移行手順

### Internal Docs

- 実装の前提
- 運用 runbook
- トラブルシューティング
- コンポーネント間の関係図

### ADR

ADR は 1 つの重要な判断を 1 つの文書にまとめます。

```markdown
# ADR: [decision title]

## Status
Accepted | Proposed | Deprecated | Superseded

## Context
[何が問題で、なぜ判断が必要か]

## Decision
[何を選んだか]

## Consequences
[良い点 / 悪い点 / トレードオフ]

## Alternatives Considered
[他の案と却下理由]
```

## 書き方

### 短く、具体的に

長い説明より、短い見出しと箇条書きのほうが読みやすいです。

### 例を入れる

使い方を説明するときは、実例を 1 つ入れます。

### 更新履歴を残す

誰がいつ何を変えたか分かるようにしておきます。必要なら changelog や ADR の status を更新します。

## レッドフラグ

- コードの説明だけで、理由がない
- 1 文書に何でも入れる
- 古いドキュメントが放置される
- ADR なのに決定理由がない
- 実例がなく、読んでも使えない

## 検証

- [ ] 読む人にとって目的が明確
- [ ] 何をしたかだけでなく、なぜそうしたかが書かれている
- [ ] 必要な例や手順が含まれている
- [ ] ADR なら代替案とトレードオフが書かれている
